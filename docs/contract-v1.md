# 러너 계약 v1

이 문서는 **zannabi-code가 밖으로 내보이는 것**을 규정한다. 소비자(대시보드·에디터·CI)는
이 계약만 알면 되고, 러너의 내부는 몰라도 된다.

계약은 셋으로 이뤄진다 — **파일 · 저널 · 능력 신고**. 그리고 소비자가 실행을 시작할 수
있도록 **실행 레시피**가 능력 신고에 딸려 있다.

> **단방향이다.** 러너는 보고하고 소비자는 읽는다. 소비자가 러너에게 지시하는 통로는
> 이 계약에 없다 — 승인·중단·라우팅은 전부 계약 밖이고, 소비자가 띄운 프로세스의 주인은
> 띄운 쪽이다. 이 원칙을 지키는 대가로 계약이 러너 구현에 묶이지 않는다.

## 왜 파일인가

소켓이나 데몬을 두면 소비자가 러너에 붙는 방법을 알아야 하고, 그 순간 계약이 특정 구현에
묶인다. 파일은 제일 멍청한 대신 누구나 읽을 수 있고, 언젠가 다른 러너가 같은 어휘로 같은
파일을 쓰면 **소비자는 바뀌지 않는다.**

---

## 1. 파일 계약

```
<프로젝트>/.zannabi/
├── runs/<run-id>/
│   ├── journal.jsonl     ← 이벤트 저널 (실시간·재개·측정을 겸한다)
│   ├── goal.json         ← intent · 게이트 · 예산 · 루프 설정
│   ├── plan.md           ← 승인된 계획
│   ├── evidence.json     ← 라운드별 게이트 결과
│   ├── rounds/round-N.patch
│   ├── diff.patch        ← 최종 변경분 (신규 파일 포함)
│   ├── report.md         ← 사람이 읽는 요약
│   └── transcript.jsonl  ← 에이전트 원본 이벤트
└── races/<race-id>/
    ├── summary.json      ← best-of-N 집계
    └── summary.md
```

**`<run-id>` = `<ISO 시각>-<슬러그>`.** 문자열 역순이 곧 시간 역순이다 — 파일 시각(mtime)은
복사·체크아웃이 바꾸므로 정렬에 쓰지 않는다. 이름은 실행이 만든 사실이고 mtime은 파일이
겪은 사건이다.

**경로를 하드코딩하지 말 것.** 능력 신고의 `evidenceLayout`이 실제 자리를 말한다.

## 2. 이벤트 저널 (`journal.jsonl`)

append-only JSONL. **한 파일이 세 가지를 겸한다** — tail하면 실시간, 재생하면 재개의
체크포인트, 끝나고 읽으면 측정 데이터. 셋을 따로 만들면 어긋날 때 어느 쪽이 진실인지
정할 수 없다.

모든 줄은 `type`과 `at`(ISO 8601)을 가진다.

| type | 언제 | 담는 것 |
|---|---|---|
| `run-started` | 실행 시작 | `contractVersion` `runId` `intent` `cwd` `budget` `runtime?` `profile?` `maxCostUsd?` `raceId?` |
| `run-resumed` | 중단된 실행을 이어받음 | `fromRound` `completedRounds` `runtime?` |
| `plan-finished` | 계획 턴 종료 | `ok` `usage?` `sessionId?` `model?` |
| `approval-requested` | 사람의 승인 대기 | `gates` `warnings` `dropped?` |
| `approval-resolved` | 승인/거부됨 | `action` `reason?` |
| `round-started` | 라운드 시작 | `round` |
| `exec-finished` | 실행 턴 종료(게이트 전) | `round` `ok` `usage?` `sessionId?` `model?` `selfChecks?` |
| `gate-started` | 게이트 하나 시작 | `round` `phase`(verify/recheck) `gate` `cmd` |
| `gate-result` | 게이트 하나 종료 | `round` `phase`(verify/recheck) `evidence` |
| `recheck-suppressed` | 재확인 판정의 한 축을 껐음 | `round` `cause` `suppressed` |
| `round-finished` | 라운드 종료 | `round` `revision` `repeatOf?` `allPass` |
| `cost-updated` | 누적 지출 갱신 | `plan` `exec` `spentUsd?` `coverage?` |
| `evidence-lost` | 증거가 사라짐 | `target` |
| `run-finished` | 실행 종료 | `status` `attempts` `detail?` |

### 어휘가 이 모양인 이유

각 줄의 기준은 하나다 — **"이것이 없으면 밖에서 상태를 재구성할 수 없는가."**

- **`approval-requested`/`resolved`가 없으면** 승인 대기 중인 실행과 멈춰 죽은 실행이
  구분되지 않는다. 둘 다 "이벤트가 끊김"으로만 보인다.
- **`exec-finished`가 없으면** 게이트를 돌다 죽었을 때 실행 턴의 지출과 세션이 사라진다.
  라운드 단위로만 기록하면 재개 후 비용 상한이 거짓말을 한다.
- **`run-resumed`가 없으면** 라운드 번호의 점프와 시각의 공백을 설명할 수 없고,
  한 번에 돈 실행과 세 번 끊겼다 이어 돈 실행이 똑같아 보인다.
- **`gate-result`가 게이트마다 나오는 이유**: 라운드 끝에 몰아 쓰면 30분짜리 게이트를 도는
  동안 밖에서는 러너가 멈춘 것과 구분되지 않는다.
- **`gate-started`가 따로 있는 이유**: 결과만으로는 **지금 무엇이 도는 중인지** 알 수 없다.
  15분 타임아웃에 걸린 게이트가 어디서 멈췄는지를 저널만 보고 말할 수 없으면 실시간 축이
  뚫린 것이다.
- **`model`이 턴 이벤트에 있는 이유**: `run-started`의 `runtime`은 실행 **전에** 쓰이므로
  우리가 지정한 값밖에 모른다. 모델은 `--model` 말고도 환경변수·프로필·CLI 기본값으로
  정해지고, 실제로 무엇이 돌았는지는 첫 턴이 끝나야 안다. 이것을 싣지 않으면
  **리포트는 아는데 저널은 모르는 상태**가 된다 — 실측에서 정확히 그 일이 있었고,
  저널만 읽는 소비자에게는 조합 비교 축이 통째로 비어 보였다.
  소비자는 `model`을 만나면 `run-started`의 `runtime`을 그 값으로 고쳐 읽어야 한다.
- **`recheck-suppressed`가 있는 이유**: 격리된 새 워킹트리의 첫 라운드는 첫 회에만 콜드
  컴파일이 얹혀 재확인 비율이 구조적으로 낮게 나온다. 그래서 그 축을 끄는데, **끄는 것의
  증상이 "경고가 없다"**이다 — 그 모양은 *억제가 일했다*와 *애초에 걸릴 자리가 없었다*를
  구분하지 못한다. 억제가 잘못 걸려 진짜 캐시 스킵을 삼켜도 아무 데도 남지 않는다는 뜻이고,
  그쪽이 거짓 초록으로 가는 경로다. **삼킨 것이 없어도(`suppressed`가 빈 배열) 줄은 남는다** —
  축을 껐다는 사실 자체가 사후 판단의 재료다.
- **`raceId`가 있는 이유**: best-of-N의 조 셋이 없으면 서로 무관한 실행 셋으로 보인다.
  같은 비교에 속했다는 사실이 사라지면 조합별 실적을 모으는 측정이 성립하지 않는다.
- **`cost-updated`가 따로 있는 이유**: 사용량 이벤트를 합치면 나오는 값이지만, 소비자가
  러너의 합산 규칙(캐시 입력을 어느 쪽이 포함하는지 등)을 다시 구현하게 만들면
  그건 계약이 아니라 숙제다.

### 읽는 쪽이 지켜야 할 것

1. **깨진 마지막 줄은 정상이다.** `kill -9`는 줄 중간에서 끊는다. 파싱 실패한 줄은
   버리고 나머지를 쓴다 — 그것 때문에 앞의 멀쩡한 수백 줄을 못 읽게 되는 쪽이 훨씬 나쁘다.
2. **모르는 `type`은 건너뛴다.** 나중 판의 러너가 쓴 파일을 옛 소비자가 읽는 경우가 그것이다.
3. **`cost-updated`는 누적값이다.** 더하지 말고 갈아끼운다.
   그리고 **중단된 턴의 지출은 여기 없다.** 어댑터는 턴이 끝날 때 사용량을 보고하므로,
   `kill`을 당한 턴이 쓴 토큰은 어디에도 잡히지 않는다. 재개한 실행(`run-resumed`가 있는
   실행)의 비용은 **실제보다 적다** — 구조적 한계이고, `--max-cost`도 그만큼 적게 센다.
   비용을 비교의 축으로 쓸 때 재개된 실행을 한 번에 돈 실행과 나란히 놓지 말 것.
4. **끝나지 않은 라운드를 완료로 세지 않는다.** `round-started`는 있는데 `round-finished`가
   없으면 그 라운드는 중단된 것이다. 완료로 치면 돌지 않은 게이트가 판정에서 빠진다.
5. **이벤트가 끊긴 것과 러너가 죽은 것은 다르다.** 저널은 프로세스의 생사를 모른다.
   지금도 도는 중일 수 있다. 판단하려면 **마지막 이벤트로부터의 무음 경과**를 보라 —
   그것이 저널이 줄 수 있는 유일한 단서다.
6. **끝나지 않은 라운드가 있다는 것은 "끊겼다"는 뜻이 아니다.** `round-started` 이후
   `round-finished` 이전은 **정상 실행의 대부분**이다(실행 턴 + 게이트 검증 전체).
   이 상태를 "중단"으로 읽으면 살아 있는 실행이 전부 죽은 것으로 보인다 —
   이 러너의 `status`가 실제로 그 버그를 냈다. 진행 중임을 말하되, 그 라운드의 게이트
   결과는 **판정의 근거로 세지 않는다**.

`zannabi status`가 이 규칙들의 레퍼런스 구현이다 — **저널만 읽고 다른 파일은 열지 않는다.**

## 3. 능력 신고 (`zannabi manifest`)

```bash
zannabi manifest   # JSON을 stdout으로
```

소비자는 이것을 보고 **어떤 화면을 그릴 수 있는지** 판단한다. 게이트 판정을 신고하지 않는
러너를 붙이면 "3개 실행 중"까지밖에 못 그리고, 신고하는 러너를 붙이면
"3개 중 2개 통과, 1개는 증거 소실"을 그린다. **화면이 러너를 알 필요는 없다 — 능력을 물으면 된다.**

| 축 | 뜻 |
|---|---|
| `gates` | 게이트를 러너가 직접 실행하고 종료코드로 판정하는가 |
| `evidence` | 실행마다 기계가 읽을 증거를 남기는가 |
| `revisionBinding` | 증거가 리비전에 결박되는가(`head` + `diffHash`) |
| `cost` | 비용을 보고하는가 |
| `liveJournal` | 진행을 실시간으로 흘리는가 |
| `resume` | 중단된 실행을 이어서 돌 수 있는가 |
| `isolation` | 실행끼리 워킹트리를 격리할 수 있는가 |
| `bestOfN` | 같은 작업을 여러 조합으로 돌려 고르는가 |
| `execShell` | **실행 턴의 에이전트가 셸 명령을 돌릴 수 있는가** |

값은 `full` · `partial` · `none`. **`full`은 예외가 없다는 뜻이다** — 조건부로 되는 것은
전부 `partial`이고, 러너는 그 조건을 밝혀야 한다.

zannabi-code가 지금 `partial`로 신고하는 다섯과 그 조건:

| 축 | 조건 |
|---|---|
| `evidence` | 증거가 대상 저장소 안에 있어 작업하는 에이전트가 지울 수 있다. 손실을 감지해 판정을 강등하지만 그것은 사후 복구지 경계가 아니다 |
| `revisionBinding` | git 저장소가 아니면 결박할 리비전이 없다 |
| `cost` | claude는 비용을 주고 codex는 주지 않는다. 그리고 **중단된 턴의 지출은 어느 런타임에서도 관측되지 않는다** — 재개한 실행의 비용은 실제보다 적다 |
| `resume` | **워크트리로 돌던 실행은 재개할 수 없다** — 브랜치 이름이 `zannabi/<runId>`로 결정되는데 워크트리를 치워도 브랜치는 남아, 재개가 같은 이름을 다시 만들려다 실패한다. `--worktree` 없이 재개하면 원본 저장소에서 돌아 그때까지의 작업이 없는 상태로 이어간다 |
| `execShell` | **여는 것이 게이트 명령뿐이다.** claude는 승인된 게이트의 `cmd`만 접두 패턴으로 받아 돌릴 수 있고(`--no-exec-shell`로 끔), codex는 `--sandbox workspace-write`라 더 넓게 돈다. `full`이 아닌 이유는 능력 부족이 아니라 설계다 — 넓게 열면 러너가 준 권한을 러너가 설명할 수 없다 |

**신고는 자랑이 아니라 계약이다.** 이 러너도 처음에는 비용만 `partial`로 적고 나머지를
`full`로 신고했다가 외부 리뷰에 잡혔다 — 못 하는 것을 신고하면 소비자가 없는 화면을
그리려다 깨진다.

실행별로 비용이 실제로 얼마를 봤는지는 `report.md`와 `cost-updated`의
`coverage`(`full`/`partial`/`none`/`not-run`)가 말한다.

#### `execShell`이 축인 이유 — 지시를 짜는 쪽이 알아야 하는 전제다

다른 축은 소비자가 **화면을 그릴 수 있는가**를 판단하는 데 쓰인다. 이것 하나는 다르다 —
**사람이 지시서를 어떻게 쓸지**를 바꾼다.

실측에서 지시서에 순서 제약을 박았다: "1단계를 넣고 게이트를 돌려 초록인지 확인한 뒤
2단계로 가라. 빨개지면 멈추고 보고하라." 두 변경이 섞이면 무엇이 깼는지 귀속이 안 되기
때문이다. 계획 턴은 그 구조를 그대로 받아 `plan.md`에 1단계/2단계를 적었다. 그런데 실행
턴이 그것을 **할 수 없었다** — `transcript.jsonl`에 권한 거부 7건이 남았고 전부 `./gradlew`였다.
컴파일은 0회, 그 상태로 404줄을 썼다.

**2026-08-23부터 이 러너는 게이트 명령을 연다**(Phase 11). 아래는 `execShell`이 `none`인
조합 — 다른 러너를 붙였거나 `--no-exec-shell`로 끈 경우 — 에서 여전히 참이다:

1. **"확인하고 다음 단계로 가라" 형태의 지시가 성립하지 않는다.** 단계별 귀속을 사람이
   지시서로 만들 수 없다. 그런 실행에서 얻은 "A는 B를 깨지 않는다"는 답은 측정이 아니라
   구성으로 얻은 것이므로, 그렇게 기록해야 한다.
2. **라운드가 유일한 피드백 루프다.** 에이전트는 검증 없이 한 라운드를 써야 하고,
   오타 하나가 라운드 하나 값이다.

신고하지 않으면 지시를 쓰는 사람이 되지 않을 것을 지시하고, **그 사실을 실행이 끝난 뒤에야
안다.** 그것이 이 축을 계약에 넣는 이유다.

**자기 확인은 판정이 아니다.** 에이전트가 게이트를 백 번 돌려도 완료는 러너가 돌린 결과로만
정해진다. 그래서 두 층은 저널에서도 갈린다 — 에이전트가 돌린 것은 `exec-finished.selfChecks`에,
러너가 판정으로 돌린 것은 `gate-result`에 남는다. **소비자는 둘을 섞어 세면 안 된다.**

### 실행 레시피 (`launch`)

순수 관측만으로는 소비자가 "새 작업"을 시작할 수 없다. 그래서 **어떻게 띄우는지**를 함께
신고한다. 자리표시자는 `{intent}` `{cwd}` `{runId}`.

프로세스 수명(중단·종료)은 계약 밖이다 — 띄운 프로세스의 주인은 띄운 쪽이다.
이 선을 지켜야 단방향 원칙이 유지된다.

---

## 4. 판정값

`run-finished.status`와 `report.md`가 쓰는 값. 소비자는 모르는 값을 만나면 실패로 취급하되
문자열 그대로 보여주는 편이 낫다 — 새 판정이 늘어날 수 있다.

| status | 뜻 |
|---|---|
| `success` | 모든 게이트 통과 (재확인을 걸었으면 재현까지) |
| `budget-exhausted` | 라운드 예산 소진 |
| `cost-exhausted` | 비용 상한 도달 — 다음 라운드를 시작하지 않았다 |
| `no-progress` | 변경분과 게이트 결과가 연속으로 동일 |
| `unreproduced-pass` | 통과가 재현되지 않음 |
| `evidence-lost` | 게이트는 통과했으나 증거가 사라짐 — **완료가 아니다** |
| `env-error` | 게이트가 이 환경에서 실행 불가 |
| `agent-error` | 에이전트 실행 실패 |
| `no-gates` | 완료 기준이 없어 거부 |
| `aborted` | 사람이 승인하지 않음 |

**`evidence-lost`를 성공으로 세지 말 것.** 게이트는 실제로 통과했을 수 있지만, 통과의 근거가
지워진 실행은 이 계약 아래에서 완료가 아니다.

---

## 5. 판 올리기

`contractVersion`은 `run-started`와 능력 신고에 함께 실린다. 소비자는 이 값으로 읽을 수
있는지 판단한다.

- **필드가 늘어나는 것은 판을 올리지 않는다.** 모르는 필드는 무시하면 되기 때문이다.
- **이벤트 종류가 늘어나는 것도 올리지 않는다.** 모르는 `type`은 건너뛰면 된다.
- **판을 올리는 것**: 기존 필드의 뜻이 바뀌거나, 있던 것이 사라지거나, 읽는 쪽 규칙이 바뀔 때.

v1의 범위는 여기까지다. **양방향 제어·원격 승인은 v1에 없다** — 별도 계약으로 다룬다.
